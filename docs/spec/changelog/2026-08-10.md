# Changelog: week of 2026-08-10 (Mon) – 2026-08-16 (Sun)

Feature additions and fixes recorded during this week.

## NumberForm (and a minimal Row) (2026-08-12)

New builtin `NumberForm[expr]`, `NumberForm[expr, n]`, `NumberForm[expr, {n, f}]`
for controlling how approximate reals and integers are displayed — significant
digits, fixed decimal places, digit grouping, scientific-notation thresholds,
padding/alignment, and custom signs/separators/multipliers/exponents. Full
option set: `DefaultPrintPrecision`, `DigitBlock`, `ExponentFunction`,
`ExponentStep`, `NumberFormat`, `NumberMultiplier`, `NumberPadding`,
`NumberPoint`, `NumberSeparator`, `NumberSigns`, `ScientificNotationThreshold`,
`SignPadding`.

- **Print wrapper.** `NumberForm` is inert (`builtin_numberform` returns `NULL`),
  so the head survives in the tree; `FullForm[NumberForm[1.23, 2]]` is
  `NumberForm[1.23, 2]` and `10 NumberForm[1.23, 2]` stays `10 1.2`. Attributes
  `NHoldRest | Protected`. All display logic is in the new `src/numberform.c`;
  `src/print.c` gains a small `SYM_NumberForm` branch in `print_standard` that
  installs a `NumberFormCtx` and recurses, plus a per-number atom hook so every
  numeric leaf (including packed-array leaves) is reformatted. `FullForm` is
  unaffected because it renders via `expr_print_fullform` directly.
- **Scientific form.** Produces Mathematica-style `1.06865*10^(13)` (the
  interpreter's default real printer still emits C-style `e+NN`); the decimal ↔
  scientific transition follows `ScientificNotationThreshold`.
- **Minimal `Row`** (`Row[{...}]`, `Row[{...}, sep]`, `Protected`) added to
  support the `NumberFormat` option's documented `Row[{#1,"e",#3}]&` assembly;
  strings print raw (OutputForm) via the existing `g_print_output_form` flag.
- **Registration.** Symbols interned in `sym_names.c`; default options in
  `options_builtin.c` (honours `SetOptions[NumberForm, ...]`); docstrings in
  `info.c`. Deviation from the reference option table: `NumberPadding` defaults
  to `{"", ""}` (no padding), matching the worked examples.
- **Tests.** `tests/test_numberform.c` covers every documented example and every
  option (18 groups, hard `ASSERT_STR_EQ`). Valgrind shows zero added leaks
  (byte-identical loss totals with and without `NumberForm`).

## Evaluator: memoize the structural hash on each Expr node (2026-08-11)

Investigating whether the symbol table or `expr_hash` contributes to the
systemic per-node evaluator constant (`MATHILDA_EVALUATOR_PERFORMANCE.md`): the
symbol table does **not** — name→definition resolution is already an O(1)
cached-pointer read on each node (`data.symbol.def`). But `expr_hash`
(`src/expr.c`) was FNV-1a **recomputed by walking the whole subtree on every
call**, and it is called per-element in `Plus`/`Times` like-term grouping,
Association key indexing (`assoc_index.c`), and the set ops
(`Union`/`DeleteDuplicates`/`Tally`, `list/setops.c`).

- **New field `Expr.hash_cache`** (`src/expr.h`): a lazily-filled memo of
  `expr_hash(node)`, sentinel `0` = unhashed (a genuine hash of 0 just recomputes
  — harmless). Filled on first `expr_hash`, reused thereafter; the recursion
  memoizes the whole subtree bottom-up. Zero-initialised in the single allocator
  `expr_alloc_node`, so every constructor and the `expr_unshare` copy start clean.
- **Invalidation contract** — `expr_invalidate_hash(e)` (inline in `expr.h`) is
  called at every in-place structural mutation of a live node: `eval_flatten_args`
  (Flat), `flatten_sequences`, the generic Orderless `qsort`
  (`src/eval.c`), and the pattern alpha-rename (`src/symtab.c`). The cache is
  benign metadata (ignored by `expr_eq`/`expr_compare`), like `symbol.def`.
- **`MATHILDA_HASH_VERIFY` build** (define-gated in `expr.c`): ignores the cache,
  recomputes every hash, and `abort()`s if a surviving cache value disagrees —
  turning any missed invalidation into a deterministic failure. Ran clean over a
  broad stress corpus, all seven `benchmarks/4x-eval-*`, and ten hash-relevant
  unit suites (`association`, `packed_list`, `sort`, `complement`,
  `intersection`, `mapat`, `replaceat`, `flatten_at`, `array_flatten`,
  `compile_assoc`).

Result: hashing the same subtree repeatedly (Association lookups, dedup/`Tally`
of repeated structural elements, re-grouping a stable sum) drops from
O(subtree) per touch to O(1). Measured up to **~14× faster** on dedup/`Tally` of
a list of repeated deep nodes (4.07→0.30 ms) with no change to results. No new
allocation (inline field), so valgrind is unchanged at the macOS baseline; full
`ctest` shows no new failures (the 6 failing suites — `zero_test`, SVD/eigen/
lapack SEGFAULTs, `partitionsq` timeout — are the documented pre-existing set).
The packed-list ⇄ materialised-`List` hash byte-identity (`test_packed_list.c`)
still holds. Docs: `MATHILDA_EVALUATOR_PERFORMANCE.md`.

## Build: de-duplicate `-lgmp`/`-lmpfr` link flags (2026-08-11)

`pkg-config --libs flint` (and GMP-ECM) re-list `-lgmp`/`-lmpfr`, which the base
`LDFLAGS` and MPFR block already carry, so the raw link line repeated them and
macOS `ld` printed `ignoring duplicate libraries: '-lgmp', '-lmpfr'`. Added a
small `LDFLAGS_DEDUP` helper in `makefile` that collapses each `-l` flag to a
single copy, **keeping its last occurrence** so a provider (`-lgmp`) still
follows every consumer (`-lflint`, `-lmpfr`, `-lecm`) — the dependency order a
static-archive link needs, and the reason `FLINT_LIBS` is appended after the base
`-lgmp`. `-L` search paths and two-word `-framework X` tokens pass through
untouched. The warning is gone; the binary links and runs identically.

## Matcher: `Condition` over a multi-element sequence blank (2026-08-11)

Fixed a conformance bug: a `Condition` wrapping a sequence blank —
`x__ /; test`, `x___ /; test`, and the named/nested/double-named forms
(`c : (b__ /; t)`, `b___ /; c1 /; c2`) — matched **only when the sequence
spanned exactly one element**. For zero or ≥2 elements it failed even with a
literal `True` guard, so the extremely common idiom
`MatchQ[{5, 10}, {b__ /; Total[{b}] == 15}]` returned `False` (WL: `True`).

Root cause in `src/match.c`: `match_args_internal` peels `Pattern`,
`Shortest`, `Longest`, `Optional` and strips `PatternTest` for sequence blanks,
but never handled `Condition[seqblank, guard]`; it fell through to the
single-element path (`min_k = max_k = 1`), so only the width-1 case — which a
`BlankSequence` also matches — slipped through. Fix mirrors the `PatternTest`
handling: strip the `Condition` layer(s) when the inner pattern is a sequence
blank / `Repeated`, remember the guard chain, and evaluate it once (via the new
`eval_seq_conditions`, inner `/;` first) at each commit point after the sequence
variable is bound. Untouched when the inner pattern is a single blank, so the
well-tested `x_ /; test` path is unchanged. `PatternTest` over a sequence and
`Condition` over a single element both already worked and still do.

Regression cases added as section 37 of `tests/match_stress_corpus.m`
(287 → 298 cases, all green). Enumeration counts cross-checked against an
independent brute-force partition enumerator.

## Matcher: fix per-guard-evaluation memory leak (2026-08-11)

Fixed a pre-existing leak in `guard_all_true` (`src/match.c`): the guard leaf
was evaluated as `evaluate(expr_copy(g))` with the `expr_copy(g)` temporary
inlined. `evaluate()` **borrows** its argument (it copies internally), so that
temporary was never freed — one orphaned `Expr` node per guard leaf that did not
evaluate to the literal `True`. Because most backtracking attempts have a
**failing** guard, this leaked ~1 node per *failed* condition check across the
whole system (every `/;` in matching, `Cases`, `ReplaceAll`, conditional
`DownValues`, …). Now the copy is held in a variable and freed. Under valgrind,
a 75,327-guard-evaluation run drops from 75,058 leaked blocks to the constant
macOS startup baseline (422 blocks); named-sequence + `Cases` workloads that lost
332 KB now lose nothing beyond baseline. No result changed — this is purely an
ownership fix.

`MATHILDA_PATTERN_MATCHER_PERFORMANCE.md` (repo root) gains **Case M**, a scaling
study of the equal-sum contiguous-partition family that surfaced both fixes. It is
a head-to-head against Mathematica 14.0 (`wolframscript`) on identical inputs: the
pattern is genuinely exponential *in Mathematica* (the reader's verbatim pattern
takes 6.75 s at N=20; a distinct-block variant 38 s at N=120), but Mathilda's
matcher prunes it to polynomial/constant cost — 100× to 135,000× faster with
identical match counts. The PDF is regenerated with `pandoc --pdf-engine=xelatex`.

## Benchmarks: evaluator-throughput suite vs Mathematica (2026-08-11)

Added seven benchmark experiments — `benchmarks/40-eval-dispatch` …
`benchmarks/46-eval-controlflow` (28 cases) — that stress the **recursive
expression-tree evaluator** (generic eval loop, matcher, rule engine) head-to-head
against Mathematica 14.0 via the existing `run_all.py` harness. Each is an
`.m`-only folder (no Python half) using the shared `bench`/`check` helpers, with
symbolic / Rational / scalar-recursion data chosen so **neither** engine diverts
to a packed-array kernel or `Compile[]`. Categories: recursive DownValue dispatch
(fib/Ackermann/mutual/`Nest`), backtracking (perf-doc cases D and M), `//.`
rewriting, per-node arithmetic (Case B family), structural `Map`/`Fold`/`Count`/
`Position`, construction/traversal, and control flow.

Findings (full writeup: `MATHILDA_EVALUATOR_PERFORMANCE.md`, repo root): two
cleanly separated results. Backtracking — Mathilda **44×–236× faster** (its
pruning turns WL's exponential search polynomial). Generic per-node throughput —
Mathilda **~1.6×–4.3× slower, median 1.89×**, uniformly across dispatch, rewrite,
arithmetic, and structural work: the same per-attempt constant factor that
`MATHILDA_PATTERN_MATCHER_PERFORMANCE.md` isolated as "Case B", now shown to be
systemic. Evaluator-only was proven two ways: the pack-gate
(`MATHILDA_PACK_DIAG=gate`) shows zero materializations except one-time O(n)
input handoffs to `MatchQ`/`ReplaceList`/`ReplaceRepeated`, and `MATHILDA_NO_PACK=1`
leaves every timing unchanged (slightly faster), so packing never touches the
measured work. All 28 value checks agree across engines.

Reproduce with
`python3 benchmarks/run_all.py --only 40,41,42,43,44,45,46 --system mathilda,wolfram`.
No built-in behavior changed; this is a measurement + documentation addition, and
the input for the evaluator per-step-constant-factor improvement work.

One incidental parser gap surfaced (not fixed here): Mathilda does not accept the
postfix `..`/`...` (`Repeated`/`RepeatedNull`) operators — the `Repeated[…]` long
form works and is what the suite uses.

## Evaluator: pooled `MatchEnv` (2026-08-11)

First optimization driven by the evaluator-throughput suite above.
`apply_down_values_def` (`src/symtab.c`) allocates and frees one `MatchEnv` — via
`env_new`, three `malloc`s — per candidate DownValue, so recursive rewriting
churns millions (`fib[28]` ≈ 2.5M envs, one per fib call × 3 rules tried).
`env_new`/`env_free` (`src/match.c`) now recycle the whole struct **including its
`symbols`/`values` arrays** through a bounded static free-list (`ENV_POOL_CAP`
256), so reuse is allocation-free after warm-up. Mirrors the existing bounded
`Expr` node pool: single-threaded, reentrant (nested matches draw more from the
pool), pooled envs are program-lifetime "still reachable". The external contract
of `env_new`/`env_free` is unchanged and `env_free` still releases each binding's
`strdup`'d key and value ref — only the arrays and struct are kept.

Effect (Mathilda ÷ WL 14.0 ratio, before → after): `fib[28]` 2.7×→2.2×
(1.57 s→1.33 s), `ack[3,4]` 3.1×→2.5×, mutual recursion 3.0×→2.2×,
`Nest[incr,0,50000]` 2.0×→1.6×; `Count`/`Position` over 5000 `f[k]` nodes crossed
into parity (suite `SLOWER` 17→15). `tests/bench_match.c` shows it directly:
`Cases` 333→196 ns/elem, `Position` 1083→583, `ReplaceAll` 390→237 (1.4×–1.9×).
It deliberately does **not** move the arithmetic-bound rows (Case B, the `//.`
folds, the Orderless sum), which are `Length`/`Plus`/list-rebuild bound, not
env-allocation bound — those are the next targets.

Verified: `bench_eval` and `bench_match` gates PASS; the env-touching unit suites
(`match`, `rule_dispatch`, `eval_timestamps`, `eval_eager_exit`, `expr_sharing`,
`return`) all pass; the 5 pre-existing ctest failures (`zero_test`, and the SVD/
eigen/lapack SEGFAULTs) fail identically with the change stashed, so they are not
regressions; valgrind on a matcher-heavy workload holds at the constant 422-block
macOS baseline with the pooled envs correctly *still reachable* (no new loss). No
result changed — this is an allocation-strategy change only.

## Evaluator: machine-integer fast path for Plus and Times (2026-08-11)

Second optimization from the evaluator-throughput suite. `builtin_plus` /
`builtin_times` (`src/plus.c`, `src/times.c`) ran several O(n) scans (NDArray
probe, neg-Plus distribution, SeriesData, inexact contagion, then
(coeff,base)/(base,exp) grouping) before combining terms — real overhead for the
ubiquitous `Plus[int,int]` / `Times[int,int]` that dominates recursive integer
code (`fib[n-1]+fib[n-2]`) and loop accumulators. Added a fast path after the
n==0/1 checks: when every argument is a machine `EXPR_INTEGER`, fold them with the
overflow-checked `ci_add_i64` / `ci_mul_i64` (Times short-circuits on a 0 factor)
and return a single integer. On overflow, or any non-integer operand, it falls
through to the existing generic path, which promotes to bigint — so results are
unchanged, including the exact bigint answers for `9223372036854775807+1` and
`3037000500^2` (checked byte-for-byte against Mathematica 14.0).

Effect (on top of the MatchEnv pool; Mathilda ÷ WL): `fib[28]` 1.33 s → 1.06 s
(2.7×→1.9× vs 1.57 s baseline), `ack[3,4]` 16.8→14.3 ms, mutual recursion
0.85→0.74 ms, `Nest[incr,0,50000]` into parity. Suite `SLOWER` count 17→14,
`AHEAD` 11→14 cumulatively. Verified: full `ctest` 199/204 (the failures are the
pre-existing `zero_test` + SVD/eigen/lapack SEGFAULTs, plus the flaky
`moebiusmu_tests` which fails at the same ~20% rate on unmodified `de6a69f`);
`bench_eval`/`bench_match` gates PASS; arithmetic edge cases (overflow→bigint, 0
factor, negatives, mixed symbolic, rationals, reals) match WL; valgrind at the
422-block baseline.

A third lever — adopting the evaluator's per-step argument buffer into the
reassembled node (`expr_new_function_adopt`) to skip a malloc+memcpy on large
`List`/`Plus` rebuilds — was built and A/B-measured but **rejected**: the win was
within noise (0–7%, mostly noise) because the large-node cases are dominated by
the operation (`replace_bindings` splice, Orderless grouping), not the reassembly
copy. Not worth a hottest-path change + new public API. The remaining suite gaps
(`//.` folds 4.2×, Case-B-untyped 3.1×, Orderless sum 2.8×) are those
operation-bound costs; see `MATHILDA_EVALUATOR_PERFORMANCE.md` for the next
targets.

## Evaluator: borrow MatchEnv keys instead of copying them (2026-08-11)

Third optimization. The `MatchEnv` pool recycles the struct and its arrays, but
`env_set` (`src/match.c`) still `strdup`'d every binding's key and `env_free`
freed it — one malloc + free per binding, millions in recursive rewriting and
structural mapping. Every `env_set` caller passes a key that already outlives the
per-attempt env: an interned symbol name (`sym->data.symbol.name`, program-
lifetime, owned by the interner) or a string literal (`"$OptionsPattern$"`). So
the key is now stored by **borrow** — no `strdup`, and `env_free`/`env_rollback`
never free it. Comparison is pointer-first (interned keys — the hot path, since
the matcher and `replace_bindings` both pass `sym->data.symbol.name` — hit
immediately) with a `strcmp` fallback so the cross-translation-unit literal
callers still match.

Effect (on top of pool + int fast path): `fib[28]` 1.06→1.05 s, `ack[3,4]`
14.3→13.1 ms, Case B typed into parity, `bench_match` `ReplaceAll` 237→187
ns/elem. Cumulative suite over the three optimizations: **17→13 slower, 11→15
ahead** vs Mathematica 14.0.

Verified: `bench_eval`/`bench_match` gates PASS; matcher correctness (nonlinear
patterns `{a_,a_}`/`{a__,b__,a__}`, `OptionsPattern`, guards, `Cases`/`ReplaceAll`)
matches WL byte-for-byte; `ctest` failures are the pre-existing/flaky set
(`zero_test`, `moebiusmu`, `bench_compile` load-gate, SVD/eigen/lapack SEGFAULTs);
valgrind at 420 blocks — two *below* the 422-block macOS baseline (fewer
allocations), no invalid access, no new loss.

## Evaluator: skip evaluate() for atomic arguments (2026-08-11)

Fourth optimization, and the one found by *profiling* rather than reasoning.
`sample` on the `//.` fold showed the entire cost in `eval_and_free`
re-evaluating the result list each pass — the per-element `evaluate()` calls in
`evaluate_step`'s argument loop, not `replace_bindings` or the match. A raw atom
(Integer/Real/String/BigInt/MPFR/NDArray/Compiled) always evaluates to itself, so
`evaluate()` there just `expr_copy`s it after paying the recursion-depth bump,
trace push, deadline check and fixed-point-loop setup *per call*. The loop now
recognises an atomic argument and goes straight to `expr_copy`, skipping
`evaluate()` entirely — provably equivalent (same pointer, so the change flag
stays clear; an atom is never an in-flight `Throw`/`Goto`). `SYMBOL` is excluded
(it may carry an OwnValue).

This is the hot path whenever a large `List` of numbers is re-evaluated — most
visibly every pass of `list //. rule`, which re-walks the whole (mostly
unchanged) list. Effect vs WL 14.0: `//.` fold on `Range[800]` **4.3× → 2.2×**
(16.8 → 9.2 ms), on `Range[400]` → 2.3×, Case B untyped 3.1× → 2.5× (its guard
builds `{x},{y},{z}` integer lists), and the `ReplaceAll`-rebuild row off the slow
list. Suite `SLOWER` 13 → 11, `AHEAD` 15 → 17.

Cumulative over the four evaluator optimizations this week (MatchEnv pool, Plus/
Times machine-int fast path, borrowed MatchEnv keys, atomic-argument skip): the
evaluator-throughput suite moved from **17 slower / 11 ahead** to **11 slower /
17 ahead** vs Mathematica 14.0, with no regressions. The remaining top gap is the
Orderless sum (`Length[Plus @@ 2000 symbolic terms]`, 3.3×) — symbolic terms, not
atoms — which is the next target. Verified: `bench_eval`/`bench_match` gates PASS;
all 28 suite value checks agree with WL (0 CHECK-FAIL); `ctest` failures are the
pre-existing/flaky set (`zero_test`, `bench_pack`/`bench_compile` load-gates,
SVD/eigen/lapack SEGFAULTs); valgrind at the 420-block macOS baseline.

## Evaluator: skip the redundant sort in builtin_plus (2026-08-11)

Fifth optimization, again found by *profiling* (`sample` on `Plus @@ Table[c[k] x,
{k, 2000}]`): ~half the time was in the final-term `qsort` and its `expr_compare`
per comparison — the grouping hash table and reconstruction were already O(1)/O(n).
But a `Plus` built in order arrives canonically ordered (`c[1] x < c[2] x < …`),
and every re-evaluation of an already-sorted sum re-sorts terms that never moved —
pervasive, since a sum flows through the evaluator to a fixed point. `builtin_plus`
(`src/plus.c`) now guards the `qsort` with an O(n) already-sorted pre-check
(`plus_cmp_ptrs` scan, sort only on the first descent found) — the same technique
already used for the Orderless fast path in `evaluate_step`. Same canonical result:
skipping a no-op sort or sorting an unsorted sum both yield the identical order.

Effect: re-evaluating a canonical 2000-term sum **1.89 → 1.12 ms (−40%)**;
`expr_compare` samples 307 → 80, `qsort` 61 → 20. The suite Orderless-sum row moved
3.3× → 3.0× — its residual is now `Table` construction and the O(n) Infinity/
contagion pre-scans, not the sort. The general win is the re-evaluation path, which
every repeated symbolic-sum evaluation (Expand, polynomial arithmetic, Simplify)
hits.

Verified: `Expand[(1+x+y)^12] = 531441`, term collection (`2x+3x+x → 6x`) and
canonical ordering (`z+a+m+b+3+1 → 4+a+b+m+z`) correct; the full Expand/Simplify/
polynomial/numeric-domain test set passes; `bench_eval`/`bench_match` gates PASS;
`ctest` failures are the pre-existing/flaky set (this change is on the symbolic
grouping path, not the packed path `bench_pack` exercises); valgrind at the
420-block macOS baseline.

## Evaluator: borrow subset/remainder slices in ordered sequence matching (2026-08-11)

Sixth optimization. Re-profiling the `//.` fold *after* the atomic-argument skip
showed the cost had moved off `eval_and_free` and into the matcher:
`match_args_internal` (`src/match.c`) allocated and copied a fresh `remainder`
array (via `extract_subset`) at **every** pattern element — even single blanks —
so one `{a_, b_, r___}` pass paid ~4 O(n) copies of the tail. But
`next_combination` is gated on `is_orderless`, so for an *ordered* (non-Orderless)
head the do-while runs exactly once with `comb = [0..k-1]`: the consumed elements
are the contiguous prefix `exprs[0..k-1]` and the remainder is the contiguous
suffix `exprs[k..]`. Both are slices of the caller's array and are read-only (type
checks, `expr_copy` into `seq_val`/`matched_val`, and the recursive callee), so
they are now **borrowed** instead of malloc+`extract_subset`. The heap copies live
in `subset_owned`/`remainder_owned` (NULL in the borrow case → the free sites are
no-ops); the Orderless combination path is unchanged. The `comb` index array is
also skipped for ordered heads (only `extract_subset`/`next_combination` read it,
both Orderless-only).

This is a **general** matcher speedup, not just the fold — every pattern match over
an ordered head's arguments now avoids the per-element subset/remainder/comb
allocation. `bench_match`: `ReplaceAll` 187 → 99.8 ns/elem, `Cases` 216 → 126,
`Position` 634 → 500, DownValue-Map 613 → 513. Fold `Range[800]` 9.2 → 8.2 ms,
bubble sort `//.` 7.6 → 3.8 ms (2×), Case D 3.8 → 1.6 ms, `ack[3,4]` 13 → 9.5 ms,
`fib[28]` and the `ReplaceAll`-rebuild row into parity.

Cumulative over the six evaluator optimizations this week: the throughput suite
moved from **17 slower / 11 ahead** to **8 slower / 20 ahead** vs Mathematica 14.0,
worst outliers 4.3× → ~2.3×, with no regressions. Verified: the 298-case
`match_stress_corpus` passes (0 failed, 0 crashed); `match_tests`,
`rule_dispatch_tests`, `bench_eval`, `bench_match` PASS; matcher correctness
(nonlinear `{a__,b__,a__}`, `Cases`/`ReplaceList` with guards, OrderlessPatternSequence,
`Plus[a,b,c] /. {x__,y__}`) matches WL; `ctest` failures are the pre-existing/flaky
set (`zero_test`, `primenu` — 2/8 flaky on the committed baseline too,
SVD/eigen/lapack SEGFAULTs); valgrind at the 420-block macOS baseline over both the
borrow (ordered) and copy (Orderless) paths — no invalid access, no double-free of
a borrowed slice.

## Evaluator: Apply/Map/Scan/MapIndexed level short-circuits + Plus/Times special-case short-circuit (2026-08-12)

Follow-up to the *evaluator throughput* campaign, targeting the one row still
trailing Mathematica in `MATHILDA_EVALUATOR_PERFORMANCE.md` — the arithmetic
sentinel `Length[Plus @@ Table[c[k] x, {k, 2000}]]` (4.69 ms vs WL 1.5 ms, 3.1×).
Profiling the three operations on its critical path (`Table` build, `@@`, the
`Plus` grouping) surfaced two avoidable, non-fundamental costs — one of them a
finding the campaign had missed.

**1 — Specialised top-level `Apply` fast path** (`src/funcprog.c`). `f @@ expr`
(default level spec `{0,0}`) went through the general recursive `apply_at_level`,
which (a) called `get_depth(expr)` — a full recursive traversal of the whole
argument tree — at every node, though its only consumer is the negative-level
branch a non-negative spec never takes, and (b) *structurally cloned every element
subtree* (~4000 interior `Times`/`c[k]` nodes for a 2000-element list) even though
Expr trees are immutable and refcount-shared. `builtin_apply` now has a
self-contained fast path — mirroring the existing `f @@ <|assoc|>` one — that, for
`ls == NULL` with a function operand, builds `f[elements…]` by refcount-sharing
each element (`expr_copy` is an O(1) refcount bump) and evaluates once. Provably
equivalent to `apply_at_level(f, expr, 0, {0,0})`. The general `apply_at_level` was
also tightened: for a non-negative spec it skips `get_depth` and returns
`expr_copy(expr)` once `current_level > spec.max` (nothing can apply at that level
or deeper), and an `apply_child` helper folds the same past-max check into the
per-child recursion so `@@@` (`Apply[…, {1}]`) — a common operation whose general
path recursed once per element *and* once per sub-element, the level-2 calls doing
nothing but refcount-share — now shares each element's arguments in O(1). Isolated
`f @@ list` over 2000 elements **~1.3 ms → ~0.05 ms**; `f @@@ list` restructuring
over 5000 elements **~0.93 → ~0.78 ms (−15%)**; the 5000-triple
`Apply[Plus, …, {1}]` benchmark **11.5 → 7.4 ms (2.47× → 1.6× WL)**. Every `Apply`
level-spec form (`@@`, `@@@`, `{2}`, `{1,2}`, `{-1}`, `{-2}`, `Heads->True`, and
deeper nesting) is pinned in `test_core_algebra.c`.

**1b — `Map` (`/@`) shares the subtree past the mapped level** (`src/funcprog.c`
`map_at_level`). Map is bottom-up, and had the *same* `get_depth`-everywhere +
descend-and-rebuild overhead — worse, because it always walked to the leaves: the
common `f /@ list` cost grew with element *depth* even though `f` only touches
level 1. The same two changes apply: skip `get_depth` for a non-negative spec, and
once past the maximum level share the whole subtree by an O(1) refcount bump
instead of descending + rebuilding it. `f /@ 5000 g[a,b,c]` **4.19 → 0.56 ms
(−87%)** and `f /@ 5000 g[h[…],h[…]]` **7.12 → 0.57 ms (−92%)** — the time is now
independent of element depth. `Map[f, expr, {0}]` (map at level 0) becomes a clean
`f[expr]` share too. Every level-spec form (`{0}`, `{2}`, `{0,1}`, `{-1}`,
`Infinity`, `Heads->True`, `Hold`-suppressed) is pinned in `test_core_algebra.c`.

**1c — `Scan` (`src/funcprog.c` `scan_at_level`)** got the same treatment. Scan
discards results so there is no rebuild, but it still descended every element's
whole subtree and called `get_depth` at each node, so `Scan[f, list]` cost grew
with element depth too. Once past a non-negative upper bound the descent now stops
(a visit needs `level <= max`, which only rises with depth), and a pure
non-negative spec skips `get_depth`; the negative-spec paths and the
leaves-before-roots order / `Throw`/`Return` control flow are untouched.
`Scan[f, 5000 g[a,b,c]]` **0.90 → 0.55 ms (−39%)**, `Scan[f, 5000 g[h[…],h[…]]]`
**1.38 → 0.52 ms (−62%)** — depth-independent. Pinned in `test_core_algebra.c`
(`test_scan`), and the existing `scan_tests`/`funcprog_through_tests` are unchanged.

**1d — `MapIndexed` (`src/funcprog.c` `mi_at_level`)** completes the set. It
rebuilds bottom-up while threading each part's `{position}`, and the depth it
accumulates into `*out_depth` is read *only* by a negative-level bound — so under a
non-negative spec it is never used, yet it descended and rebuilt every element's
whole subtree to compute it. Two guards fix that: past the max level share the
subtree (return early, depth left at 1), and at the deepest wrapping level share the
node instead of descending + rebuilding (its children are all past max, so the
rebuild would just reproduce it). `MapIndexed[f, 5000 g[a,b,c]]` **5.55 → 1.57 ms**,
`MapIndexed[f, 5000 g[h[…],h[…]]]` **8.39 → 1.60 ms** — depth-independent, and now
**1.2× WL 14.0** (down from 4.1×; it stays just above WL because it builds a
position vector + two-arg wrapper per element, which no short-circuit removes).
Every level-spec form, the `{i,j,…}` positions, `Heads->True`, and `Association`
`Key[k]` positions are pinned in `test_core_algebra.c` (`test_mapindexed`); the
existing `mapindexed_tests` is unchanged.

**2 — Fused special-case short-circuit in `Plus` and `Times`** (`src/plus.c`,
`src/times.c`). Both ran five independent full O(n) pre-scans before term grouping
— NDArray probe, neg-Plus distribution (Plus only), SeriesData, inexact contagion
(with a size-n `malloc` taken *before* the check), Infinity/Indeterminate — and for
an ordinary symbolic or rational sum/product every one finds nothing. A single
detection pass now decides whether any could act; if not, execution jumps straight
to grouping. The predicate is a provably-correct superset of "some pass would act"
(NDArray→`is_ndarray`, neg-Plus→`is_neg_of_plus`, series→`is_series_data`,
contagion→`arg_is_inexact` — exported from `numeric.c` for this, matching
`numeric_contagion_args`'s own trigger — Infinity→`classify_plus_term`/the inline
Times check), so skipping the passes when it is false is exactly equivalent. The
guarded passes are otherwise byte-for-byte unchanged.

**Result.** `Length[Plus @@ Table[c[k] x, {k, 2000}]]` **4.69 → 2.95 ms (−37%,
3.1× → 2.0× WL)**; the sibling `bench_eval` row "orderless sort (Plus 1200)"
dropped from 0.27 to ~0.19 norm. The residual is now dominated by `Table`'s
per-element symbolic-`Times` evaluation (2.43 ms of the 2.95 ms) — the systemic
per-node evaluator constant, whose largest remaining lever is the fixed-point
double pass (`builtin_times`/`builtin_plus` unconditionally rebuild and trip the
change flag, forcing a confirm-stable step). That is a core-evaluator change of
much broader blast radius and is left for a separate, measured effort.

**Tests.** New `tests/test_core_algebra.c` (wired into CMake as
`core_algebra_tests`) pins Plus/Times/Power/Divide/Apply/Length/ordering/Table
against WL-checked FullForm, deliberately covering the paths these changes touch:
every `Apply` level-spec form (`@@`, `@@@`, `{2}`, `{-1}`, `Heads->True`, empty,
single, atomic) and every guarded Plus/Times special case (cancellation, Infinity,
ComplexInfinity, Indeterminate, contagion, radical fusion, trig canonicalisation).
`tests/bench_eval.c` gains the three flagship regression rows mandated by the perf
doc — `fib[24]` (dispatch), Case B typed (matcher constant), Plus-2000 (this
sentinel). Verified: `core_algebra_tests`, `eval_tests`, `sort_tests`,
`expand_tests`, `collect_corpus_tests`, `power_corpus_tests`, `evaluate_tests`,
`regression_tests`, `match_tests`, `match_extensive_tests` PASS; the 298-case
`match_stress_corpus` passes (0 failed/0 crashed); `bench_eval` PASS with the new
baselines armed; valgrind identical to the empty-session macOS baseline
(13,440 B / 420 blocks, 0 invalid read/write/free) over the Apply fast path and the
Plus/Times short-circuit paths — no new leak.

## Compile[]: `Norm[v, p]` two-arg forms + inline-vector auto-compilation (2026-08-12)

`Norm` had a `Compile[]` lowering only for the bare `Norm[v]` / `Norm[m]`
(2-norm / spectral), and a `Norm[{f[x], …}]` body could not auto-compile at all.
Two independent gaps, closed by operand kind. No interpreter behaviour changed —
both fixes live entirely in `src/compile/`, and the packed/NDArray `ndla_norm`
path is unchanged.

**1 — Declared-array two-arg forms (new `V_NORM` opcode).** `Norm[v, 1]`,
`Norm[v, Infinity]`, `Norm[v, k]`, `Norm[v, 2.5]`, and the matrix `Norm[m, 1]` /
`Norm[m, Infinity]` / `Norm[m, "Frobenius"]` now lower to a machine `Real`. The
second argument is a compile-time literal but not always a machine scalar
(`Infinity`, `"Frobenius"`), so it is baked into the instruction immediate
`imm.r` — `0` = none, `+Inf` = Infinity, `NaN` = "Frobenius", a finite positive
value = that `p` (rebuilt as an Integer when integral, since LAPACK keys the
matrix path on Integer 1/2). The VM (`OP_V_NORM`, a `K_ARR` op modelled on
`V_NDRED`) rebuilds `Norm[array, p]` and delegates to `ndla_norm`, so the
compiled answer is bit-identical to the interpreter's NDArray path by
construction. Validity mirrors `ndla_norm` exactly (`nd_norm2_encode` in
`compile_ndtables.c`): a rank-1 operand takes any positive `p` or Infinity; a
rank-2 operand takes `{1, 2, Infinity, "Frobenius"}`; an induced matrix `p`-norm
with `p ∉ {1, 2, Infinity}`, a string method on a vector, and int/complex
operands decline cleanly to the interpreter. The bare `Norm[v]`/`Norm[m]`
reduction (ND_REDS) is untouched.

**2 — Inline vector construction (auto-compilation).** A `Norm[{e1, …, en}, p]`
whose operand is a `List` literal (not a declared array) was the reason a
`Table[Norm[{Sin[x], Cos[x], x}], …]` body bailed wholesale — the compiler could
not lower the inline vector. It now expands to the same scalar arithmetic the
interpreter's `builtin_norm` uses (`norm_try_expand` in `compile.c`, shared by
`emit_node` and `infer_type`): `Sqrt[Σ Abs[ei]^2]` (p=2/Frobenius),
`Σ Abs[ei]` (p=1), `Max[Abs[ei]]` (Infinity), `(Σ Abs[ei]^p)^(1/p)` (general p),
expandable exactly where `builtin_norm`'s symbolic branch is (rank-1 under any p,
any rank under "Frobenius"). This produces inline scalar code with **no
per-iteration buffer allocation** — strictly better than packing a short vector —
and unblocks `Norm[{…}]` bodies inside `Plot`/`Table`/`NIntegrate`/`FindRoot`. A
rank-2 list under an induced norm (needs an SVD) is not expandable and falls
through unchanged.

**Verified.** `CompileDiagnostics` reports `Compiled -> True` for every reported
form and `False` for the correct declines; compiled values equal the interpreter
(bit-identical for the array delegate, within machine tolerance for the scalar
expansion); the `MATHILDA_COMPILE_DIAG=1` auto-compile probe no longer prints
`[compile] interpreting`. New tests in `tests/test_compile_transforms.c`
(`test_cf_norm_array_vector`, `_array_matrix`, `_list_literal`); the compile,
NDArray, normalize, and lstsq suites pass; `make check-c99` clean.

## Packed arrays: `Im` narrowing kernel — off the NOT_AWARE list (2026-08-12)

`Im` had an NDArray projection kernel but sat on `pack.c`'s `NOT_AWARE` list, so
on the *invisible* auto-packed-List surface it materialised to the scalar List
path — `Im[Range[1., 10^7]]` cost ~3.9 s where the sibling `Re` cost ~0.17 s
(~22×). The reason was exactness: `Im` of a real is the exact `Integer 0`, and a
projection kernel would have written `0.0` into a float64 buffer, an observable
wrong element head (the same real→integer trap that kept `Floor`/`Sign` off the
fast path until they got narrowing kernels on 2026-07-30).

Fix: give `Im` a narrowing pair (`NDKU_ImInt` in `src/ndkernels.c`, `to_int`) —
`to_int_r`/`to_int_i` write an `NDT_INT64` zero buffer from real/integer input
(unconditionally 0; the imaginary part of any real is 0, finite or not, so unlike
`Sign` there is nothing to reject), while a COMPLEX input still takes the `ndk_Im_c`
projection arm (the imaginary part, a Real), which `ndarray_map_unary`'s narrowing
branch skips for complex dtypes. `Im` then comes off `NOT_AWARE` and is implicitly
aware via its kernel.

Result: `Im[Range[1., 10^7]]` **3856 ms → 151 ms (~25×)**, matching `Re`; element
heads are identical to the List path (`Im[{2., 3.}] === Take[Im[Range[1., 300.]], 2]`
is `{0, 0}`, both exact `Integer`), a real `NDArray` gives an `int64` zero array,
and a complex `NDArray` still gives the Real imaginary parts. No behaviour changed
— the packed answer was already exact via the slow path; this makes the buffer
path produce it directly.

Incidental: `Abs` and `Im` are now hand-written kernels rather than `UK_PROJ`
macro expansions, dropping the two unused projection descriptors (`NDKU_Abs`,
`NDKU_Im`) so `src/ndkernels.c` compiles clean under `-Wall -Wextra`
(`-Wunused-const-variable`); `ndk_Abs_c`'s body is unchanged.

## Chop and Clip: buffer fast paths + Compile lowerings (2026-08-12)

`Chop` had no fast path on any surface, and `Clip` degraded to the interpreter
whenever it clipped against exact (default `{-1,1}`) bounds. Both are now fast on
the machine-buffer, `Compile[]`, and auto-compilation surfaces, with no change to
any answer. The exactness obstacle for both is the same real→integer trap `Im`
just hit — a chopped/clipped element is an exact `Integer`, which no uniform Real
buffer holds — so each keeps a buffer only where the result is uniform.

- **Chop NDArray fast path** (`chop_ndarray` in `src/core.c`; `Chop` added to
  `pack.c`'s AWARE). An auto-packed `List` used to be materialised before it
  reached Chop (~40× an aware head). Now a cheap alloc-free scan keeps the buffer
  untouched when NOTHING chops (`Chop[Range[1.,10^7]]` **1362 → 131 ms**); when
  something chops, a rank-1 buffer builds the mixed `{…, 0, …}` result in ONE pass
  off the elements (an all-zero result re-packs to int64), and higher ranks take
  the general delist. Complex/int64 buffers delist. Value-identical to
  `chop_recursive`.
- **Chop `Compile[]` + auto-compilation** (`compile_emit_mathfn.c`,
  `compile_infer.c`). `Chop[x]` / `Chop[x, δ]` (δ a literal) lower branchlessly to
  `x * (Abs[x] >= δ)` (the UnitStep mask-multiply, no new opcode) → `Real`; the
  chopped value is a machine `0.` (a CompiledFunction returns machine types). A
  machine integer never chops → identity. So `Chop[…]` now auto-compiles inside
  `Plot`/`Table`/`NIntegrate`/`FindRoot`.
- **Clip scalar `Clip[x]`** (default bounds) now lowers as `Min[Max[x,-1.],1.]`,
  filling the `na==1` gap; the explicit-bounds scalar form was already
  `Min[Max[x,lo],hi]`.
- **Clip exact-bounds buffer, three-way scan** (`ndstruct_clip`). The exact-bound
  path now distinguishes: nothing clips → the Real input; a MIX of clipped
  (Integer) and unclipped (Real) → the exact List path; and EVERYTHING clips to a
  finite exact-Integer bound → a uniform `NDT_INT64` buffer. That last case is the
  common `Clip[reals, {-1,1}]` over out-of-range data: **`Clip[Range[1.,10^7]]`
  4633 → 158 ms (~30×)**. Rational/infinite bounds still take the List path.

Verified: `check-array-exactness` 0 MIXED (Chop/Clip buffers stay single-headed or
degrade correctly), `check-packed-aware` OK (Chop now aware, AWARE 175→176);
compiled == interpreter (Chop/Clip maxdiff 0.0); short == packed element heads for
every Clip regime; `chop_tests`, `clip_tests`, `compile_transforms_tests` (new
`test_cf_chop`, `test_cf_clip_default`, `test_chop_packed_*`,
`test_clip_packed_exact_bounds`) pass; `check-c99` clean; 0 leaked bytes.
Inherent residual: a *partial*-chop / *partial*-exact-clip over a large buffer is a
mixed result the evaluator must walk element-by-element (matching Mathematica,
which also unpacks) — the buffer path covers the uniform cases.

## FindClusters beyond one dimension

`FindClusters` accepted only a flat list of real scalars; a list of vectors —
Wolfram's own second example — returned unevaluated. It now clusters:

- **equal-length numeric vectors** in any dimension,
- **colours** (`RGBColor`, `GrayLevel`, `Hue`, `CMYKColor`), whose arguments are
  coordinates, so a colour is a point in its own space and needs no
  colour-specific code,
- **strings**, on `EditDistance`.

```mathematica
In[1]:= FindClusters[{{1, 1}, {1, 2}, {9, 9}, {9, 8}}]
Out[1]= {{{1, 1}, {1, 2}}, {{9, 9}, {9, 8}}}

In[2]:= FindClusters[{"cat", "cot", "dog", "dig"}, 2]
Out[2]= {{"cat", "cot"}, {"dog", "dig"}}
```

**One dimension is unchanged, by construction.** The file's structure is now a
spanning tree with exact edge weights, and on a line the minimum spanning tree
*is* the sorted adjacency chain — so the general code reduces to the original
algorithm exactly there. The 132 existing acceptance rows are the proof and were
required to stay green; 35 rows were added.

**Exactness survives in n dimensions** because ranking uses *squared* Euclidean
distance, which is rational for rational input and monotone in the true distance.
`FindClusters[{{1/3, 1/7}, {1/3, 1/7 + 1/10^20}, {5, 5}}]` groups the two
near-identical exact vectors rather than collapsing them through a double.

Scope limits, stated rather than discovered:

- Only `Automatic`, `"Agglomerate"` and `"SpanningTree"` accept the new element
  kinds. The other seven methods read a sorted one-dimensional projection and
  decline instead of running on data where it is meaningless.
- Vectors and strings are capped, both being quadratic where a sort avoids that
  only on a line. The ceiling depends on which spanning-tree builder runs — see
  the machine-precision section below.
- `Rational` and `Complex` are numbers, not points: `{1/2, 1/3, 10}` clusters as
  three reals. Point heads are an explicit list precisely so that
  `Rational[1, 2]` is never read as a pair of coordinates.

## Distance functions

Seven functions that did not exist. `Names["*Distance*"]` returned only
`GraphDistance`, while `FindClusters`' `DistanceFunction` option accepted
`EuclideanDistance` and friends as **inert symbols** — which is why its
documentation could truthfully claim all the choices behaved alike.

| Function | Value |
|---|---|
| `EuclideanDistance[u, v]` | `Sqrt[Sum Abs[u_i - v_i]^2]` |
| `SquaredEuclideanDistance[u, v]` | `Sum Abs[u_i - v_i]^2` |
| `ManhattanDistance[u, v]` | `Sum Abs[u_i - v_i]` |
| `CosineDistance[u, v]` | `1 - (u . Conjugate[v]) / (Norm[u] Norm[v])` |
| `EditDistance[u, v]` | Levenshtein distance, strings or lists |
| `HammingDistance[u, v]` | positions differing, equal lengths required |

Exact input gives exact output where the value is rational; complex components
contribute their modulus (`Abs` before squaring, as Mathematica defines it);
symbolic input survives as an expression. Every value was cross-checked against
`wolframscript`, including two conventions that are not derivable:
`CosineDistance` of a zero vector is `0` rather than `Indeterminate`, and
`HammingDistance` on unequal lengths is left unevaluated.

The `DistanceFunction` documentation was corrected: the equivalence of the
Euclidean family is a statement about **one dimension**, where they are monotone
transforms of one another. It does not hold for vectors.

## Fixes

- **`FindClusters` with an explicit count was quadratic.** `FindClusters[data, 10]`
  over 100,000 points took 2.24 s against 0.087 s for `Automatic` on the same
  input, growing fourfold per doubling. The union-find introduced with the
  spanning-tree rewrite had no path compression, so when few edges are cut the
  surviving components form one long chain and every `find` walks it. `Automatic`
  hid the bug because many cuts leave many short components. With path halving
  and union by rank: **2.24 s → 0.083 s**, and linear again.

- **`Abs` and `Sign` decline on rationals with bigint components.**
  `Abs[-1/10^20]` does not evaluate while `Abs[-1/7]` does. This is a
  pre-existing bug, not introduced here, but it silently blocked every exact
  high-precision distance and so made `FindClusters` refuse exact vectors at that
  scale. The distances route around it by taking the sign through the exact
  comparator; **the underlying `Abs`/`Sign` gap remains and is worth fixing
  separately.**

## FindClusters: a machine-precision spanning tree, 219x faster on vectors

Clustering vectors was capped at 2000 points and spent nearly all its time
allocating expressions: exact Prim computes O(n^2) distances, and each one built
and evaluated a chain of `Expr` nodes to keep the comparison exact.

For input whose coordinates are *already* machine numbers, that buys nothing --
there is no precision beyond a double to preserve. Such input now takes a
double-precision Prim; only the n-1 chosen edge weights become expressions, so
allocation drops from O(n^2) to O(n). Input with a `Rational`, bigint or MPFR
coordinate keeps the exact builder, which is the only one that can order it
correctly.

| 2-D points | before | after |
|---:|---:|---:|
| 500 | 95 ms | 0.62 ms |
| 1000 | 398 ms | 2.0 ms |
| 2000 | 1.49 s | 6.8 ms |

**219x at n=2000**, which lifts the machine ceiling from 2000 to 20000 points
(0.81 s there). The exact path keeps its 2000 cap.

Nothing is given up. Distinctness was never decided from a distance on either
path -- it compares the elements with the exact comparator -- so
`FindClusters[{{1/3, 1/7}, {1/3, 1/7 + 1/10^20}, {5, 5}}]` still groups the two
near-identical exact vectors. Two builders for one definition is a standing risk,
so a test clusters the same points both ways (as integers, which are machine, and
divided by a constant, which makes them exact) and requires the partitions to
match, including over 400 random points.

Integer coordinates are required to be within 2^53 to take the fast path, since
beyond that a double stops representing integers exactly and the two builders
would quietly disagree.

## FindClusters accepts a visible NDArray

`FindClusters[NDArray[{1., 2., 10.}]]` clusters. It used to return unevaluated —
and that was documented behaviour rather than an oversight, so this is a
deliberate change with a test row rewritten to match.

The two array surfaces reach a builtin differently, which is the whole reason only
one of them was broken. The packing transparency gate (`src/eval.c`, step 2.7)
materialises a *packed* list for any head not on `src/pack.c`'s `AWARE` list, so
that surface always worked. It tests only `is_packed_list`, though, so a
**visible** `NDArray[...]` passed straight through to a builtin whose shape guard
is `is_listq` — which an `EXPR_NDARRAY` fails. Unevaluated, with no message.

Rank 1 is read as scalars and rank 2 as points, each giving the same partition as
the equivalent `List`. Rank 3 and above still decline: a list-valued component is
not a coordinate, and `fc_probe_shape` already rejected it.

It is a materialise guard, not a buffer fast path, and `FindClusters` stays off
`AWARE` — with an `EXEMPT` entry in `tools/check_packed_aware.py` recording why,
alongside `Cases` and `FlattenAt`, which are exempt for the same reason. Reading
the buffer directly would mean giving up what makes the answers exact: the
spanning tree orders rationals and bigints through `internal_subtract`, the
boundary set compares *elements* because `2^60` and `2^60 + 1` are distinct yet
project to the same double, and the clusters are emitted from the input elements
themselves. Opting in to `AWARE` would also stop the gate materialising a packed
list, which is exactly the plain `args[]` all of that needs.

No speed is given up either. Every value in an `NDArray` is machine by
construction, so `fc_all_machine` is true and the machine spanning-tree builder
runs — the same one a machine `List` takes, with the 20000-point ceiling from the
previous entry.

Ownership is handled by splitting the body into a helper that takes the data list
as a parameter. There are eighteen `return NULL` paths, and the materialised list
must outlive the cluster emission and be freed on all of them; one caller that
owns the temporary and one callee that only borrows it cannot leak or double-free.

## DistanceFunction selects a metric instead of being discarded

`FindClusters[..., DistanceFunction -> ManhattanDistance]` now clusters by
Manhattan distance. It used to validate the name, return true, and store nothing:
`FcOpts` had no field for the choice and `fc_pair_distance` hardcoded squared
Euclidean.

On a line that was harmless and arguably correct — every accepted metric is a
monotone transform of `|a - b|` there, so all four induce the same ordering of gaps
and the same partition. Above one dimension it is a wrong answer rather than a
missing feature: Manhattan and Euclidean rank pairs differently in the plane, and a
user asking for one and silently getting the other has no way to notice.

```
FindClusters[{{0, 0}, {0, 11}, {8, 6}}, 2]                                → {{{0,0}}, {{0,11},{8,6}}}
FindClusters[{{0, 0}, {0, 11}, {8, 6}}, 2, DistanceFunction -> ManhattanDistance]
                                                                          → {{{0,0},{0,11}}, {{8,6}}}
```

Squared Euclidean weights those edges 121, 100 and 89, so the tree is `{89, 100}`
and cutting its heaviest edge isolates `{0,0}`. Manhattan weights them 11, 14 and
13, so the tree is `{11, 13}` and cutting its heaviest isolates `{8,6}`.

`EuclideanDistance` and `SquaredEuclideanDistance` are deliberately ONE case rather
than two. Squaring is monotone on non-negatives so it preserves edge ranking, and
the threshold test `d > 3 median(d)` holds exactly when `d² > 9 median(d²)` — so the
two always produce the same partition. Collapsing them also avoids taking a square
root of an exact value: `Sqrt[2]` is irrational, and an exact ordering that has to
compare irrationals is a substantially harder problem than this needs.

The threshold factor now tracks the metric rather than the kind. It was squared for
any POINT input because Euclidean weights are squared distances; under Manhattan
the weights are plain sums of absolute differences, so keeping the squared factor
would have applied a threshold nine times too large — a silent, plausible-looking
wrong answer.

Scalar input is untouched: the metric is applied only to points, since a line's
weights are plain exact differences that no accepted metric can change. The
one-dimensional answers of all ten methods are pinned in
`tests/test_findclusters_scalar_pin.c` and unchanged.

`DistanceFunction` takes a metric, not a string — `EuclideanDistance`, not
`"EuclideanDistance"` — the reverse of `Method`. A quoted string leaves the call
unevaluated, which is now pinned, because the two conventions sit next to each
other and are easy to swap.

Both spanning-tree builders were wired, and a test clusters the same points as
integers (machine, double builder) and divided by three (exact rationals, Expr
builder) under Manhattan, requiring identical partitions. Two builders for one
definition is a standing risk, and a metric wired into one of them would make the
answer depend on how the numbers happened to be written.

## MeanShift and NeighborhoodContraction cluster n-dimensional points

Both now work on vectors, not only scalars. Four of the ten methods are
dimension-general: `Agglomerate`, `SpanningTree`, and these two.

```
FindClusters[{{0,0},{1,0},{0,1},{1,1}, {20,20},{21,20},{20,21},{21,21},
              {0,40},{1,40},{0,41},{1,41}}, Method -> "MeanShift"]
  -> the three squares, and the same for NeighborhoodContraction and in 5-D
```

This is one implementation, not a second one beside the 1-D kernel, and three
observations are what let it be:

**The scalar case is not a special case.** `d->val` is a row-major n × 1 buffer
indexed by input position, which is exactly the layout `d->coord` has at dim 1. So
one pointer serves both and the branch disappears.

**The median spanning-tree edge weight generalises the median adjacent gap
exactly.** On a line the minimum spanning tree *is* the sorted adjacency chain, so
its edge weights are precisely the gaps the 1-D code took the median of. Better,
the *mean* edge weight reproduces `(max − min)/(n − 1)`, because those gaps sum to
the range — and that was the 1-D fallback for a zero median, so the fallback
generalises for free. Weights are converted to lengths before the median is taken:
rooting afterwards happens to agree for the median, since a root is monotone, but
not for the mean.

**Merging by union-find reproduces the adjacent-difference pass.** The 1-D merge
walked sorted neighbours, which vectors have no analogue of. Uniting every pair
within tolerance agrees with it on a line, because a point lying between two others
is closer to each than they are to one another — so pairs within tolerance are
always reachable through adjacent steps.

`fc_merge_modes` was deleted rather than kept: it was correct and irreducibly
one-dimensional, and `-Werror=unused-function` turns leaving it into a build
failure, which is the right pressure.

The cap is divided by the dimension. The 1-D limit was chosen for
Θ(iterations × n²); dim multiplies that, so it is not left to grow silently.

Scalar answers are unchanged — all ten methods' 1-D partitions are pinned, and the
new length scale is shared by every method's default radius, so this was the change
most likely to move one. A dim-1 point and the equivalent scalar are asserted to
agree, including where the answer is coarse: with three points the median of two
edge weights averages 1 and 98 into a scale of 49.5, which cannot resolve them, and
both forms return one cluster.

**A quirk found and recorded rather than silently fixed.** When the median edge
weight is zero — any tie-heavy input — the scale falls back to the mean, i.e.
range/(n − 1), and the flat kernel's default radius is three times the scale. At
n = 4 that radius is *exactly* the range, so an outlier sits precisely on the
inclusion boundary and `NeighborhoodContraction` merges everything however far away
it is placed. This is pre-existing 1-D behaviour, identical in both
dimensionalities, so changing it would move a pinned answer and belongs in its own
deliberate change.

Strings still decline for both: there are no coordinates to shift toward higher
density. The gap methods continue to handle them through edit distances in the tree.

## FindClusters: `"KMeans"` in n dimensions

`FindClusters[points, k, Method -> "KMeans"]` now clusters vectors, taking the count
of dimension-general methods to five of ten (`Agglomerate`, `SpanningTree`,
`MeanShift`, `NeighborhoodContraction`, `KMeans`).

**A second implementation, deliberately, not a generalisation.** The previous port
unified MeanShift's two dimensionalities because the n-D form provably reproduced
the 1-D answers. Nothing like that holds here: the 1-D kernel seeds at quantiles of
the sorted distinct values and the n-D one seeds farthest-first, and two
initialisations are two algorithms that settle in different local optima. Routing
one through the other would move pinned answers, so unification is a behaviour
change to argue for on its own, not a tidy-up. The n-D suite now asserts that the
two paths agree on the same data written both ways, which is what would catch them
being merged by accident.

What survives the port is the shape — assign, move the centres, repeat. What does
not is every mechanism the 1-D kernel used to do it quickly: a merge walk over
midpoints of *sorted* centres, a scalar mean over a contiguous run, and an
empty-cluster repair that picks value boundaries in sorted order. All three need a
total order vectors do not have.

**Farthest-first initialisation, and why it is not arbitrary.** The first centre is
the point nearest the centroid; each subsequent one is the point farthest from
everything already chosen.

- It is deterministic, as the quantile seeding it replaces was. There is no
  `RandomVariate` in the tree yet, and this keeps reproducibility from needing one.
- Seeding from the centroid rather than from index 0 makes the result **independent
  of the order the points were given in** — asserted against a permutation and a
  reversal — which a k-means has no business depending on.
- Every centre is a distinct data point, so each cluster starts owning at least
  itself. Distinctness is guaranteed rather than hoped for: the count is capped at
  the distinct-value count, so while fewer than that many centres are chosen some
  point is still at nonzero distance from all of them. A cluster that does empty is
  reseeded at the point currently farthest from its own centre — the order-free form
  of the 1-D boundary repair, and one that cannot loop, since the reseeded centre
  then owns at least that point.

**The ceiling is on `n × k × dim`, not on `n` — the shift methods' cap invites the
wrong shape by analogy.** Lloyd's algorithm is *linear* in `n`, and cheaper than the
spanning tree already built for the same input, so capping `n` would decline work
the builder had just finished paying for. 20000 machine points in ten dimensions is
admitted by `FC_NDIM_MACHINE_MAX_N`, and there is no reason for k-means to be the
step that refuses it: measured **0.60 s** at `k = 3` and at `UpTo[8]`, recovering
the planted groups exactly. What is declined is `k` on the order of thousands at
that size, where the assignment scan becomes a hundred near-quadratic passes. The
bound is conservative in one direction and knowingly so: `k == n` converges in a
single iteration, since farthest-first hands every point its own centre, so it is
refused by a budget that assumes the iteration count — refusing a degenerate request
is cheaper than modelling it.

`Automatic` remains refused for `KMeans` in *both* dimensionalities. That is
`FC_ALLOWED`, not a porting gap, and it is now asserted on both surfaces so the
decline is never mistaken for an unported path and "fixed". `UpTo[k]` is the
data-driven form, and a bare `k` is obeyed exactly — twelve points asked for nine
clusters return nine.

`DistanceFunction` applies: on `{{0, 0}, {0, 11}, {8, 6}}` the apex is nearer the
origin under Euclidean (10 against 11) and nearer the far point under Manhattan
(14 against 11), so the pair that clusters flips. Asserted where the metrics
genuinely differ, since a case both answer identically proves nothing.

Equal points are still never split — the fold over zero-weight tree edges is
kind-agnostic and covers the port for free. KMeans is the method most able to break
that on its own, since a count larger than the distinct-point count could only be
met by splitting a duplicate pair; the count yields instead.

One pin moved deliberately: `tests/test_list.c` recorded
`FindClusters[{{1, 1}, {9, 9}}, 2, Method -> "KMeans"]` as returning unevaluated,
and it now returns `{{{1, 1}}, {{9, 9}}}`.

## FindClusters: `"DBSCAN"` in n dimensions — and one kernel instead of two

`FindClusters[points, Method -> "DBSCAN"]` now clusters vectors: real
ε-neighbourhoods in place of a sorted window, and union-find in place of a
left-to-right sweep. Six of the ten methods are dimension-general.

**The interesting part is that this one *replaced* the 1-D kernel rather than
sitting beside it, and that KMeans could not.** The old kernel linked only
*adjacent* sorted pairs — "consecutive points, one of them core" — where DBSCAN
specifies any pair within ε joined through a core point. Those are not obviously
the same rule. At the default `MinPoints -> 2` they provably collapse together,
since a point with any neighbour inside ε is then automatically core and both
reduce to single linkage at ε; above that default the argument runs out.

So the question went to the pin suite rather than being settled by reasoning: all
22 one-dimensional pins pass through the general kernel unchanged, which says the
general rule is answer-preserving on a line and there is no case for a second
copy. That is exactly the test the pin suite was written for two iterations
earlier, and it is what distinguishes this port from KMeans, where the pins would
have moved and two paths were therefore the honest outcome.

`fc_eps_window` went with the old kernel — DBSCAN was its only caller, and
`-Werror=unused-function` turns leaving a dead 1-D helper behind into a build
failure.

Noise still becomes singletons rather than being dropped, which is what keeps the
result a partition of the input: `{{0,0},{1,0},{0,1},{1,1},{99,99}}` gives the
square and then `{{99, 99}}` alone. `MinPoints` does visible work — raised to 3 on
`{{0,0},{1,0},{50,50},{51,50},{52,50}}`, neither of the first two is core, so both
fall out separately while the triple survives. An explicit
`"NeighborhoodRadius"` reaches the n-D kernel too, not only the default derived
from the length scale.

Strings are now the *only* thing DBSCAN refuses: an ε-neighbourhood needs
coordinates, and edit distances live in the tree, which is what the gap methods
read.

One more pin moved on purpose: `test_list.c` recorded
`FindClusters[{{1, 1}, {9, 9}}, Method -> "DBSCAN"]` as unevaluated.

## FindClusters: `"JarvisPatrick"` in n dimensions

Real k-nearest-neighbour lists and a real set intersection replace index
arithmetic on contiguous windows. Seven of the ten methods now cluster vectors.

Lists are kept sorted by *index* rather than by distance so the intersection is a
linear merge, and selection breaks ties toward the lower index so the result does
not depend on scan order. A point is a member of its own neighbour list, matching
the 1-D window (which spans `sv[i]` *and* its k nearest) and the classical
formulation — two points that are each other's neighbours already share those two
members.

**The default `NeighborCount -> 5` needs groups with more than five points, and
this is worth stating because it looks like a bug.** A 5-nearest-neighbour list
cannot fit inside a 4-point blob, so it must reach into a neighbouring blob, which
then links them: the three 4-point blobs used elsewhere in the test suite come
back as *one* cluster, and `"NeighborCount" -> 3` recovers all three. The 1-D
kernel behaves the same way (a `k` clamped to `n - 1` puts every point in one
window), so this is the algorithm on data too small for its default. The n-D blob
test therefore uses eight points per blob; asserting the merge would have pinned a
data-sizing artefact instead of the method.

**This port corrected the procedure DBSCAN established.** DBSCAN was unified onto
one kernel because all 22 one-dimensional pins passed through the general rule.
The same experiment here also leaves all 22 pins passing — and still moves an
answer that `list_tests` covers and the pin file does not:

```
FindClusters[{1, 2, 10, 12, 3, 1, 13, 25},
             Method -> {"JarvisPatrick", "NeighborCount" -> 2}]
  1-D kernel:  {{1, 2, 1}, {10, 12, 13}, {3}, {25}}
  n-D kernel:  {{1, 2, 3, 1}, {10, 12, 13}, {25}}
```

So the criterion is "does any *covered* 1-D answer move", not "do the pins pass" —
the pin file is a floor, not the whole 1-D contract. The two rules differ because
the 1-D kernel counts shared neighbours as the overlap of two contiguous windows
and links only adjacent sorted pairs, where this one intersects sets over all
pairs. The general rule is very likely the better one, but adopting it on a line
moves a checked answer, so JarvisPatrick keeps two paths like `KMeans` and the
change is left to argue on its own.

Cost is the same order as the other neighbourhood methods: 0.0198 s at n = 2000 in
ten dimensions, against 0.0177 s for DBSCAN on the same input.

Also measured while checking DBSCAN's own ceiling, since the previous entry
asserted a cap without a number: DBSCAN is 1.73 s at n = 20000 in ten dimensions,
scaling cleanly 4x per doubling (0.0013 / 0.0046 / 0.0177 s at 500 / 1000 / 2000).
That is the same order as the spanning-tree build it follows, so the cap stands.

## FindClusters: `"KMedoids"` in n dimensions

Eight of the ten methods now cluster vectors; only `Spectral` and
`GaussianMixture` remain. KMedoids reuses `fc_lloyd_ndim` rather than duplicating
it — farthest-first initialisation already seeds with actual data points, which is
exactly what a medoid needs — and switches only the update step behind a flag, the
same shape the 1-D `fc_lloyd` already had.

**The medoid search is a different complexity class, not a different constant, so
it carries its own tighter ceiling.** A mean is `O(n·dim)`; a medoid compares every
member against every other member of its cluster and is `O(n²·dim)` however small
`k` is. The bilinear budget that admits 20000 points at a small `k` is therefore the
wrong bound here, and the cleanest evidence that the second ceiling is real is that
the *same* 2000×10 input separates the two methods: `"KMeans"` clusters it,
`"KMedoids"` declines.

**The two dimensionalities disagree, and the n-D answer is better — measured, not
asserted.** On `{1, 2, 3, 10, 11, 12, 25}` at `k = 3`:

```
1-D kernel (quantile seeding):     {{1, 2, 3}, {10}, {11, 12, 25}}   cost 16
n-D kernel (farthest-first):       {{1, 2, 3}, {10, 11, 12}, {25}}   cost  4
```

where the cost is the method's own objective, the total distance from each member
to its cluster's medoid. So this is not a port artefact to be hidden behind an
agreement assertion — the 1-D kernel is sitting in a four-times-worse local
optimum. Both are pinned as they actually behave, and adopting farthest-first on a
line is left as its own deliberate change.

**A negative result, recorded so it is not re-derived.** No test claims that
`"KMedoids"` and `"KMeans"` produce different *partitions*: 26 constructed cases
(hand-built plus a 20-point parameter sweep over an outlier's distance and a second
group's offset) all agreed. On well-separated data the medoid/mean distinction
shows up in where the centre *sits*, and only turns into a different partition when
a mean is dragged across a decision boundary. The discriminating evidence for the
port is the objective gap above and the ceiling difference, both of which separate
the methods on real input.

## FindClusters: `"Spectral"` in n dimensions

Nine of the ten methods now cluster vectors; only `GaussianMixture` remains.

**The step that looked one-dimensional was not the one that was.** The 1-D kernel
cuts the widest jumps in the *embedding*, and an embedding is one scalar per point
however many dimensions the data has — so "sort and cut the widest gaps" is a
statement about the Fiedler vector, not about the input. Sorting by embedding value
instead of by data value carries the rule across unchanged, and the k-means-on-the-
embedding step that seemed necessary turned out not to be.

Two real changes: the affinity is `exp(-(dist/h)²/2)` with `dist` from
`fc_dist_pos` and `h` from `fc_scale_ndim`; and the affinity matrix is
*precomputed* rather than rebuilt inside the power iteration. The 1-D kernel
recomputes `exp()` for every pair on every iteration, which costs nothing extra on
a line but would multiply by `dim` here. Precomputing is arithmetically identical,
so it is a speed change only; at the `FC_SPECTRAL_MAX_N` ceiling the matrix is
2000×2000 doubles, 32 MB.

**Connected components are read before the Fiedler vector, and this is the
substance of the port.** The multiplicity of the zero eigenvalue of the normalised
Laplacian equals the number of connected components, so with `c` components the
null space is `c`-dimensional and the leading non-trivial eigenvector is defined
only up to a rotation inside it; power iteration lands on whichever member the seed
favours, which separates two groups at best. This is the *easy* case rather than a
corner case — better separation means smaller cross-affinity, and
`exp(-(60/1.5)²/2)` is zero in double precision, not merely small. Three blobs in
five dimensions came back with two merged and the third split for exactly this
reason, while the same three in two dimensions survived on the luck of the seed.
Components are now read off with union-find, which is what the spectrum says to do
and needs no eigensolver. Asked via `UpTo[k]` for fewer clusters than there are
components, the nearest components merge first, ranked by the spanning tree —
the spectrum cannot choose, because every partition respecting components has zero
cut and all are optimal, so the tie-break has to come from somewhere.

**A threshold finding, and its mirror.** The natural count now compares embedding
jumps against the **mean** jump, not the median. A spectral embedding earns its keep
by collapsing within-cluster distance toward zero, so with tight clusters most jumps
are ~0, the median is ~0, and three times it admits nearly everything: two
well-separated 4-point blobs came back as *four* clusters and three as *five*, while
`UpTo[3]` recovered all three perfectly — the embedding was right and only the count
was wrong. The mean is correct because the jumps sum to the range, so
"wider than three times the mean" is a statement about a jump's share of the whole
spread; it gives 1 on uniform data and `c` on `c` tight clusters, and a lone outlier
inflates it only by `1/m`. The mirror image is why the two paths stay separate:
on raw *data* gaps the median is right and the mean under-counts, so routing scalars
through the n-D kernel turned `{{1,2,3},{10,11,12},{25}}` into
`{{1,2,3,10,11,12},{25}}`. Each statistic is right in its own domain.

**A crash fixed.** `n < 3` has to be handled on the point path itself. Falling
through to the 1-D branch reaches `fc_scatter`, which indexes `d->order` — `NULL`
for point input — so `FindClusters[{{1, 1}, {9, 9}}, Method -> "Spectral"]`
segfaulted. It now returns one cluster, and that row is pinned.

## FindClusters: `"GaussianMixture"` in n dimensions — and the first `src/ml/` module

**All ten `FindClusters` methods now cluster vectors.** The only input still declined
above one dimension is a list of strings, which has no coordinates.

**This one's kernel deliberately does not live in `find_clusters.c`.** The EM fit is
`src/ml/gmm.c`, behind a buffer-level API taking a row-major `n × dim` array rather
than a `FindClusters` internal. The reason is not tidiness: `find_clusters.c` holds
55 static functions and exports exactly *one* symbol, so nothing in it is reachable
from a second builtin — and `GaussianMixture` is the first clustering kernel with two
real consumers, this `Method` and the `LearnDistribution` learner of the same name.
A 56th static function would have forced the distribution learner to re-implement EM.
`ClusteringComponents`, `ClusteringTree`, `Dendrogram` and `NearestNeighborGraph` are
blocked on the same wall. What stayed in `find_clusters.c` is what is genuinely its
business — turning a fit into a partition, and choosing `k`; what moved is what is
nobody's in particular: covariances, Cholesky factors, Mahalanobis distances and a
log-density (`ml_gmm_logpdf`, which is what makes the fitted object a *density*
rather than a partition, and the entry point the distribution learner will use).

Note for anyone adding a directory under `src/`: `makefile`'s `SRC` line is an
explicit per-subdirectory glob list, **not** recursive, so a new directory is
silently never compiled until it is named there. `tests/CMakeLists.txt` collects
sources explicitly too.

Three things are not mechanical generalisations of the scalar kernel:

- **The variance floor becomes a ridge, not a clamp.** `if (var < floor) var = floor`
  has no direct matrix reading; the honest translation is "no direction may have
  variance below the floor", which is a clamp on eigenvalues and costs an
  eigendecomposition per component per iteration. Adding `floor·I` raises every
  direction by exactly the floor, enforcing the same lower bound for one add — it can
  only overshoot, never undershoot — and it is what makes the factorisation succeed on
  a component with fewer points than dimensions.
- **The E-step runs in log space through log-sum-exp.** A component's density is a
  product of `dim` factors, so in linear space a point a few standard deviations from
  every mean underflows the total to zero. The scalar kernel answered a zero total by
  handing that point *uniform* responsibilities — survivable on a line, and actively
  wrong here, since the outlying points are the informative ones.
- **A component whose covariance will not factorise falls back to diagonal** rather
  than failing the fit, so a rank-deficient component (fewer points than dimensions,
  or collinear ones) does not take the whole model with it.

The Cholesky is written in-house rather than routed through `mat_lapack_dpotrf`.
LAPACK is right for a large factorisation, but `dim` is a feature count — single
digits in practice — and this runs once per component per iteration where the cost is
entirely the `O(n·k·dim²)` E-step. Twenty lines with no conditional dependency on
`USE_LAPACK` is the better trade at this size, and the call site is one function if
that ever changes.

**Unified onto one kernel, like DBSCAN.** Routing scalars through the n-D fit left
every covered 1-D answer unchanged — all 22 pins *and* the `list_tests` capability
rows — so the 1-D body and its scalar EM (`fc_gmm_fit`) were deleted rather than kept
alongside. That is the second unification of the eight ports; `KMeans`, `KMedoids`,
`JarvisPatrick` and `Spectral` each kept two paths because the general rule moved a
covered answer.

**Full covariance needs more points per component than dimensions,** and the tests say
so rather than working around it. `k_max` is capped at `n/(dim + 1)`, the minimum for
a non-degenerate scatter matrix, so the nine-point five-dimensional probe the other
methods use correctly returns **one** cluster while twenty-four points per blob
recover all three. Same shape of finding as JarvisPatrick's `NeighborCount` not
fitting inside a 4-point blob: the default is wrong for the data, not the code.
Singular components are asserted directly — four identical points, and five collinear
ones — because the ridge and the diagonal fallback are the only reasons they work.

## Machine learning family 2 begins: `Standardize`, `PrincipalComponents`, `src/ml/pca.c`

The first **new builtins** of the machine-learning work rather than ports, and the
start of Wolfram's DimensionReduction family. Neither `Standardize` nor
`PrincipalComponents` existed; nor do `DimensionReduce`, `MultidimensionalScaling` or
`LatentSemanticAnalysis` yet, which are the next items.

New docs page: [`docs/spec/builtins/machine-learning.md`](../builtins/machine-learning.md).

**Kernels are buffer-level in `src/ml/pca.c`, following `gmm.c`.** Column means and
standard deviations are wanted by `Standardize`, by PCA, by a future `Classify`'s
feature scaling and by `LearnDistribution`'s Multinormal; the symmetric
eigendecomposition is wanted by PCA, by MDS and by LSA. Writing them against an `Expr`
would have put all of that behind a builtin.

**A surface bug found and fixed before it shipped.** The obvious way to return a
machine matrix is `na_build_matrix`, the exported bridge the LAPACK builtins use — and
it returns a **visible `NDArray`**, whose head is `NDArray`. So the first version had
`Standardize[data] === {{…}}` evaluating to **False** against the literal a user would
write, while `Inverse[m] === {{…}}` is `True`: `Inverse`, `Dot` and `LinearSolve` all
return head `List` and let the evaluator's packing gate hold the buffer. The builtins
now build plain `List`s, and a test row pins `Head[…] == List` so the next new builtin
does not repeat it. This was found by *comparing surfaces*, not by assuming the bridge
was appropriate — worth recording because nothing in the bridge warns about it.

**Eigenvector signs are canonicalised**, and this is what makes the output testable at
all. An eigenvector is defined only up to sign, and LAPACK's `dsyev` and the in-house
Jacobi fallback disagree about which they return — so without canonicalisation the
same input gives sign-flipped components depending on how the binary was linked. Each
component is flipped so its largest-magnitude loading is positive.

No `#ifdef USE_LAPACK` at the call site: `mat_lapack_dsyev` is declared
unconditionally and the no-LAPACK build links a stub returning nonzero, so "did it
work" is the same question either way and the Jacobi fallback hangs off the status.
Jacobi is hand-written for the reason `gmm.c`'s Cholesky is — the in-tree symmetric
solvers are `static` to their translation units, `dim` is a feature count, and this
runs once per call.

Assertions in `tests/test_ml_pca.c` are properties any correct implementation must
satisfy, not numbers this one happens to produce, since there is no prior behaviour to
pin:

- `Standardize` must equal `(x - Mean[x])/StandardDeviation[x]` written out by hand,
  which also forces the `n - 1` divisor to match `StandardDeviation`'s — a divisor
  mismatch is invisible on a mean but not on a scale.
- The PCA rotation is orthogonal, so **total variance is preserved** while being
  concentrated in the leading component. Both halves matter: a projection that lost
  variance would still pass a "PC1 is largest" check. Measured 14.0 before and after.
- Rank-one data (five points on a line) must put *exactly* zero in the second
  component.
- `Correlation` must differ from `Covariance` where the columns' scales differ, since
  that is the only case in which the option means anything — a test passing for both
  would prove nothing.
- A constant column standardises to `0`, not `Indeterminate`.

## `DimensionReduce`, with PCA, LSA and classical MDS

Closes the data-in/data-out surface of Wolfram's DimensionReduction family.
`DimensionReduce[data, k]` and `DimensionReduce[data, k, Method -> m]` for
`"PrincipalComponentsAnalysis"` (default), `"LatentSemanticAnalysis"` and
`"MultidimensionalScaling"`.

**The three methods turned out to be one algorithm with three ways of forming the
symmetric matrix to decompose**, which is why they share `ml_sym_eigen_desc` instead
of each carrying its own linear algebra:

| Method | Matrix decomposed |
|---|---|
| PCA | covariance of the **centred** columns |
| LSA | Gram matrix `X'X`, **uncentred** — which *is* a truncated SVD |
| MDS | double-centred squared-distance matrix (Torgerson) |

Two consequences worth stating. LSA needed **no separate SVD path**: the
eigendecomposition of `X'X` gives the same right singular vectors, so the single `if`
that skips the centring is the entire mathematical difference between principal
components and a truncated SVD. And skipping it is not an optimisation — a
term-document matrix is sparse and non-negative, and centring destroys both properties
along with the meaning of a zero entry.

**The strongest piece of evidence in this family so far:** classical MDS on Euclidean
distances reproduces PCA *exactly* — agreement to 1e-8 on the test data — by a
completely different route, an `n × n` double-centred distance matrix rather than a
`dim × dim` covariance. Because the two paths share almost no code, that agreement is
evidence about **both** implementations in a way no self-consistency check could be.
It is asserted in the suite, on absolute values, since an eigenvector's sign is
arbitrary and the two matrices have different shapes so the sign canonicalisation
cannot force the same choice for both. It also means MDS earns its keep only when the
distances come from somewhere other than the coordinates.

Also asserted: reducing to `k` gives *exactly* the first `k` principal components
rather than a separately-fitted `k`-component model, which is what would catch a
reducer that re-derived its axes from a truncated matrix.

`"MultidimensionalScaling"` is capped at 2000 rows, its matrix being `n × n` — the same
order of ceiling, for the same reason, as `FindClusters`' `"Spectral"`.

Asking for more dimensions than the data supports **returns unevaluated rather than
padding with zeros**, since padding would look like a successful reduction to a caller
checking only the shape. An unknown `Method`, a non-positive `k`, an omitted `k` and a
flat list all decline as well.

**Deliberately not implemented:** a `DimensionReducerFunction` applicable to *new*
data. That is a trained model, and the model representation is being designed with the
`Predict` family rather than invented twice — the same reasoning that put the GMM fit
in `src/ml/` before `LearnDistribution` existed.

## Machine learning family 3: `Predict`, `LinearModelFit`, and the trained-model representation

The design task two earlier families deferred to here. `DimensionReduce` could not
return a reusable reducer and `Classify` cannot return a classifier until a **fitted
model** can be represented as an expression that survives storage and re-application.
Decided once, in `src/ml/predict.h`.

**The decision: a plain expression whose head is a symbol and whose arguments are
ordinary expressions.** Two richer designs were rejected, and the obvious one is among
them:

- **A new opaque node type, following `EXPR_COMPILED`** — the codebase's existing
  precedent for a callable carrying binary state, and the answer this was expected to
  reach. Rejected because `EXPR_COMPILED` exists to hold a *VM program*: bytecode, a
  register file, a reference count. A fitted linear model is a short vector of numbers.
  A new node type means new cases in `expr_copy`, `expr_free`, `expr_eq`, `expr_hash`,
  `expr_compare` and `print.c` — touching the core of the system — to store what the
  existing types already hold. Machine precision is not an argument either: a packed
  List already holds a dense double buffer and is still an ordinary List.
- **An `Association` payload**, the most Wolfram-ish shape. Rejected because it buys
  nothing positional arguments do not, while adding an Association dependency to every
  read. Named properties are still exposed — through the *application* path
  (`p["Coefficients"]`), which is where a user reaches for them anyway.

**Application reuses the evaluator's existing composite-head chain.** `eval.c` already
dispatches `Function[…][args]` and `Association[…][key]` by matching on the head's own
head; a fitted model is one more branch in the same chain, so no new evaluation concept
is introduced. A probe function keeps `eval.c` from having to know the model head names.

`Predict[data]` takes either `{features -> value, …}` or a matrix whose last column is
the response, and returns a `PredictorFunction` answering `"Method"`, `"Coefficients"`
and `"FeatureCount"`. `LinearModelFit` returns the same object under the name a reader
of regression code looks for; Wolfram's regression diagnostics (`RSquared`, standard
errors, ANOVA) are **not** implemented and not approximated.

**The verification that matters is agreement with an independent implementation.**
`Fit` already solves least squares in this tree by a different route, and it and
`Predict` agree — `Fit` gives `1.0 + 2.0 x` where `Predict` gives `{1.0, 2.0}`, and the
test asserts agreement at two evaluation points rather than comparing presentations.
That is the same kind of cross-check that validated classical MDS against PCA, and it
is worth more than any hand-chosen constant.

`ml_ols` solves the **normal equations** by Gaussian elimination rather than calling
LAPACK's `dgels`. `dgels` is numerically better — a QR avoids squaring the condition
number — but `A'A` is `(dim+1)` square, a handful of rows at any realistic feature
count, and the normal equations make the singular case *directly* detectable as a zero
pivot. That matters because **declining on a singular fit is deliberate behaviour**
here: collinear features have no unique fit, and a pseudo-inverse would return one of
infinitely many answers while looking like a success.

One test of mine was wrong rather than the code: `Head` of an unevaluated composite
application is the whole head `PredictorFunction[…]`, not the symbol, so the assertion
that a wrongly-shaped input does not produce a prediction became `NumberQ[…] == False`.

## `Predict` with `"NearestNeighbors"`, and `src/ml/mlutil`

`Predict[data, Method -> "NearestNeighbors"]`, with
`Method -> {"NearestNeighbors", "NeighborsNumber" -> k}` to set the neighbour count.

**A nearest-neighbour predictor has no fitted parameters — the training set *is* the
model**, which is why it costs nothing to fit and everything to apply. It is stored as
one matrix with each row's response appended, so features and labels cannot drift
apart. `k` defaults to 3 (enough to average away one noisy response, few enough to stay
local) and is clamped to the number of training rows. Selection is a partial
insertion into a `k`-sized list rather than a sort of all `n`, with ties keeping the
earlier row so the answer does not depend on scan order.

That the parameter slot holds a coefficient list for one method and a training matrix
for another is not a wart — it is why the model representation is *positional with a
method tag* rather than a fixed schema, and why application dispatches on the tag.

**`"NeighborsNumber"` on a `"LinearRegression"` is refused, not ignored.** Silently
accepting a meaningless option hides a real mistake. So does an unrecognised
sub-option, and a non-positive `k`.

**Cross-checked against the existing `Nearest`.** A 1-neighbour predictor must return
the label of whatever `Nearest` picks, and it does — at six query points including both
sides of a midpoint (2.4 → 2.0, 2.6 → 3.0), so the tie-breaking region is actually
exercised. The limit is worth stating: `Nearest` supports only the one-neighbour scalar
form here (its `k` form and its point form decline), so this validates neighbour
*selection* at `k = 1` and says nothing about the averaging, which is asserted directly.

**`src/ml/mlutil.{c,h}`** promotes the helpers that had reached three copies —
`ml_list_of_reals`, `ml_list_matrix`, `ml_read_data`, plus `ml_sqdist`. Two copies is a
coincidence; three is a shared need, and that was the stated trigger.

**An extraction deliberately NOT done.** `find_clusters.c` has a real
machine-precision metric layer (`fc_dist_pos`, `fc_dist_to_point`) that honours a
`DistanceFunction` — and it stays private. Extracting it means introducing a metric
enum in `src/ml` and rewriting a 2600-line file whose 22 one-dimensional answers are
pinned: real risk to a finished family, bought for a four-line squared Euclidean. The
honest trigger is a `src/ml` consumer that needs *metric selection* rather than one
that needs Euclidean — the moment `Predict` or `Classify` gains a `DistanceFunction`
option, that layer has its second real consumer and the refactor pays for itself. This
is the same "extract at the second real consumer" rule that put the GMM fit in
`src/ml`, applied in the direction of *not* acting.

One test of mine was wrong for precisely the reason recorded in this project's own
guidance — "a case where both branches answer identically proves nothing". The
k-NN-differs-from-linear assertion used data that was exactly `y = 10x`, where a
neighbour average at an interior point *equals* the linear prediction, so it passed
while demonstrating nothing. Rewritten on `y = x²`, which has curvature a line cannot
follow.

## `DimensionReduction`: a reusable reducer, and the representation paying off

`DimensionReduction[data, k]` returns a `DimensionReducerFunction` applicable to data it
was never trained on. Wolfram's split is kept: `DimensionReduce[data, k]` gives the
reduced *training* data, `DimensionReduction[data, k]` gives the *reducer*. This closes
the last open row of the DimensionReduce family, which had been deliberately blocked on
the model representation since two iterations earlier.

**The retrofit needed no new machinery**, and that is the point worth recording. A
reducer is the *same* positional, method-tagged object a `PredictorFunction` is, so
adding it required no new `EXPR_` node type, no new evaluation concept, and no change to
`eval.c` beyond the existing probe recognising one more head. That is the return on
having designed the representation once, in one place, rather than per family — and it is
the evidence that the design was the right size rather than merely the smallest.

**The one real hazard was centring, and it is a bug that hides well.** New rows must be
centred on the **training** column means. The plausible alternative — centring each
incoming batch on its own mean — gives *all zeros* for a single point, which is
indistinguishable from a correct projection on data that happens to sit near the origin.
The test therefore trains on data with means `{104, 210}` and asserts both halves: a
point *at* the training mean projects to `0` (which identifies *which* mean is
subtracted), and a point away from it projects far from `0` (which is what fails on the
bug). A symmetry row is added on top: points equally far either side of the training mean
must project to equal magnitudes of opposite sign.

Verified against the sibling builtin too: on its own training data the reducer reproduces
`DimensionReduce` exactly, so the two cannot have drifted apart in centring or
projection.

Only `"PrincipalComponentsAnalysis"` is offered as a reducer. That is a real limit rather
than an omission: classical MDS has no out-of-sample extension without an explicit one
(Nyström), and an LSA reducer would need the term-document vocabulary carried along with
it.
